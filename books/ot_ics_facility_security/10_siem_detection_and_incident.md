# 第10章：SIEMによる統合ログ検知・可視化とインシデントレスポンス

---

## 1. はじめに

前章（第9章）では、OT網の内部に侵入した攻撃者（Kali Linux）が、ARP Spoofingを用いてBACnetの門扉制御やRTSPの監視カメラ映像を密かに掌握する「Red Teaming（レッドチーム演習）」を実施しました。

本章からは攻守を入れ替え、防御側の視点に立つ**「Blue Teaming（ブルーチーム演習）」**を行います。

一度OT網の内側に入り込まれたL2中間者攻撃に対し、防御側はどのように検知し、どのように対処すればよいのでしょうか。本章では国際標準（IEC 62443 / NIST SP 800-82）のベストプラクティスに則り、パケット監視を用いた「OT-IDS」を構築してインシデントレスポンスに挑みます。

---

## 2. 国際標準（IEC 62443 / NIST SP 800-82）が求めるネットワーク監視

本演習に入る前に、防御の拠り所となる国際標準が「OTネットワークの監視」についてどのように定義しているかを確認しておきます。

### ① NIST SP 800-82 (ICSセキュリティガイド)
NISTは、ICS（産業制御システム）環境における異常検知の手段として、制御通信に遅延や影響を与えない**「アウトオブバンド（帯域外）でのパッシブネットワーク監視」**を推奨しています。また、エンドポイントのログだけでなく、スイッチ等の通信経路上でパケットを直接監視するIDS（侵入検知システム）の導入をベストプラクティスとして挙げています。

### ② IEC 62443 (産業用自動制御システムのセキュリティ)
IEC 62443では、ネットワークを機能的・物理的な要件に基づいて「ゾーン」に分割し、ゾーン間の通信経路を「コンジット」として定義します。防御側は、このコンジットを通過するすべてのトラフィックを可視化し、異常をリアルタイムに検知できる能力（DPI: Deep Packet Inspection等）を備えることが求められています。

> **💡 OTネットワーク監視の絶対法則**
> **「稼働中のプラントシステムに一切の負荷をかけず、ネットワークの要衝（コンジット）で全パケットをパッシブに監視する」** ことが、OTセキュリティにおける絶対的なベストプラクティスとなります。

---

## 3. 境界防御の限界：「ログに残らない」という死角

前章で攻撃を実行した際、DMZのJump Server等には一切のアラートやログが残りませんでした。

なぜなら、ARP Spoofingを用いたL2（レイヤ2）レベルの中間者攻撃は、OT網の同一サブネット内のブロードキャストドメインで完結しており、ファイアウォールやルーターの境界を通過しないからです。

「侵入を防ぐ（境界防御）」だけでは、内部犯行や一度侵入された後の横展開（Lateral Movement）に対して無力です。これが現在のOTセキュリティにおける最大の課題と言えます。

---

## 4. パッシブ監視（NSM）こそがOTの生命線

インシデントの兆候に気づいた防御側が最初に陥りがちなのが、「とりあえずJump Serverに入ってWiresharkでパケットを見る」という初動アプローチです。

しかし、実際にJump Server上でキャプチャを行っても、ModbusやBACnetなどの制御パケットは一切見えません。L2スイッチは宛先MACアドレスを見てパケットを転送するため、HMIとPLC間で交わされる通信（および攻撃者によるMITM通信）は、無関係なJump Serverのポートには流れてこないからです。Jump Serverは完全に「盲目」の状態に置かれます。

そこで、IEC 62443やNIST SP 800-82が強く推奨するのが **「NSM（Network Security Monitoring：ネットワークセキュリティ監視）」** です。

ネットワークの中核となるスイッチのミラーポート（SPAN）等を用いて通信パケットを受動的（パッシブ）にコピーし、それを専用の「OT-IDS」で監視することで、稼働中のプラントに影響を与えずに全容を把握するアプローチです。今回はこの設計に倣い、全パケットを監視できる環境（`ot-ids`コンテナ）を構築しました。

---

## 5. IDSでのフォレンジック（パケットキャプチャ）と手動解析の限界

OT-IDSの重要な役割の一つに「フォレンジック（事後証拠保全）のためのフルパケットキャプチャ」があります。

今回は、SPANポートに接続された `ot-ids` コンテナ上で `tcpdump` を稼働させ、攻撃時の通信をすべて記録したパケットキャプチャ（`attack_trace_full.pcap`）を取得しました。

![](https://static.zenn.studio/user-upload/97a04daab7d4-20260723.png)

パケットを精査すると、「同じMACアドレス（攻撃者）が異なるIPアドレスを名乗っている」不審なARPパケットや、通常とは異なるModbus/BACnetのペイロードが紛れ込んでいることがわかります。

しかし、毎秒膨大な数のパケットが流れるプラントのネットワークにおいて、これを「人間の目でリアルタイムに見つけ出す」のは不可能に近く、事後解析においても非常に時間を要します。

だからこそ、パケットから自動的に脅威を抽出し、人間にわかりやすい形でアラートを上げる「IDS（侵入検知システム）」が必要になります。

---

## 6. リアルタイム検知エンジン（DPI）の実装

事後解析では対応が遅れるため、パケット解析ロジックを「リアルタイム検知エンジン（OT-IDS）」へと進化させました。

Python（Scapy）の `sniff()` 関数を用いてネットワークインターフェースを常時監視し、異常を検知した瞬間にHMI（Node-RED）へWebhook（HTTP POST）を送信する仕組みです。これは、IEC 62443が求める「コンジット」におけるDPI（Deep Packet Inspection：パケット詳細解析）要件を満たします。

```python
# realtime_ids.py（抜粋）
def process_packet(pkt):
    # 1. ARP Spoofing検知：同一IPに対して異なるMACが観測された場合
    if pkt.haslayer(ARP) and pkt[ARP].op in (1, 2):
        ip = pkt[ARP].psrc
        mac = pkt[ARP].hwsrc
        if ip in arp_table and arp_table[ip] != mac:
            send_alert_to_hmi("ARP Spoofing (Conflict)", ip, mac)

    # 2. Modbus不正書き込み検知：FC 0x05（Write Single Coil）の監視
    if pkt.haslayer(TCP) and pkt.haslayer(Raw) and pkt[TCP].dport == 502:
        if len(pkt[Raw].load) >= 8 and pkt[Raw].load[7] == 0x05:
            send_alert_to_hmi("Modbus Memory Override", pkt[IP].src, "Unknown")
```

## 7. アラートの可視化と初動対応（HMI連携）

OT-IDSが異常を検知した際、ログに書き出すだけでは現場のオペレーターは気づけません。そこで、検知したアラートを即座にHMI（Node-RED）の画面に表示させる仕組みを構築しました。

![](https://static.zenn.studio/user-upload/24208178a272-20260723.png)

画面上部に「SECURITY ALERT」という警告がポップアップし、攻撃者のIPアドレスやMACアドレスが現場のオペレーターに即座に伝わります。

さらに、HMIのダッシュボードには**「EMERGENCY ISOLATE（緊急遮断）」**というボタンを配置しています。このボタンを押すと、Node-REDの裏側で以下のコマンドが実行されます。

```bash
iptables -A INPUT -s <ATTACKER_IP> -j DROP
```

これにより、攻撃者（Kali Linux）からHMIに対する直接的通信（不正なModbus書き込みコマンド等）を、L3（IP）レベルで即座に遮断することができます。

---

### 💡 考察：ホストベース防御の限界と「可用性」への影響

一見すると解決したように見えますが、この方法にはOTセキュリティの観点から決定的な弱点が存在します。

* **L2（ネットワーク層）の攻撃は止まっていない**: `iptables` による遮断は、あくまで「HMI自身が特定のIPからの通信を無視する」というホストベースの自己防衛に過ぎません。攻撃者は依然としてネットワーク上に存在し、ARP Spoofingによるパケットのばら撒きを続けているため、通信の阻害状態は解消されません。
* **「可用性（Availability）」への深刻な影響**: OT環境において最も重視されるのは「可用性（システムが止まらないこと）」です。攻撃者がARP Spoofingを用いてHMIとPLC（Sensor）の間に割り込んでいる（MITM）状態において、HMI側で攻撃者のIPをブロックしたとしても、HMIとPLC間の正常なModbus通信が復旧するわけではありません。

真の意味で「隔離（Isolate）」を行い、システムの可用性を迅速に回復させるためには、HMI上のファイアウォールだけでは不十分です。IDSのアラートをトリガーとして、マネージドスイッチのAPIを叩き、攻撃者が接続されている物理ポート自体をシャットダウン（VLAN隔離）するといった、**ネットワークレベルでの自動対応（SOAR）** が不可欠となります。

---

## 8. おわりに：統合SOC/SIEMへの道

今回のお取り組みを通して、「パケットベースのリアルタイム検知（NSM/IDS）」の有効性を確認できた一方で、初動対応（EMERGENCY ISOLATE）におけるホストベース防御の根本的な限界が明らかになりました。

単一ホストの `iptables` では、L2の攻撃を排除することも、制御通信の可用性を回復させることもできません。この課題を解決するには、IDSのアラートを人間が画面の前で待ち構えて対処するのではなく、ネットワーク機器との連携による自動化（SOAR）や、複数拠点のアラートを一箇所で俯瞰できる統合監視基盤が必要になります。

次章（第11章）では、OT-IDSや各機器のログをSIEM（統合ログ監視基盤）や Observability 基盤に集約し、相関分析とダッシュボード化を行う「統合SOC（Security Operations Center）」の実践へと進みます。
